# Архитектурные решения

Каждое решение: что выбрано, почему, какие варианты отброшены.

## ADR-01. Модульный монолит вместо микросервисов
**Решение.** Одно приложение FastAPI (API + статика + планировщик) и одна база.
**Почему.** Пользователей единицы–десятки, нагрузка мала; монолит проще развернуть на
ноутбуке и перенести на сервер компании, а модули сервисного слоя всё равно разделены.
**Отброшено.** Микросервисы (импорт, граф, мониторинг отдельно) — лишняя сложность
развёртывания и межсервисного взаимодействия без выигрыша при такой нагрузке.

## ADR-02. PostgreSQL + PostGIS
**Решение.** Хранение геометрии и пространственные запросы в PostGIS.
**Почему.** Привязка концов линий (`ST_DWithin`), длины по эллипсоиду (`geography`),
точка на линии по расстоянию (`ST_LineInterpolatePoint`), пересчёт систем координат
(`ST_Transform`) — всё есть в базе и выполняется с пространственными индексами.
**Отброшено.** SQLite/SpatiaLite (слабее для многопользовательской работы), хранение
координат числами без пространственного индекса.

## ADR-03. Фронтенд на JavaScript без сборщика вместо Vue
**Решение.** HTML + ES-модули + Leaflet, файлы отдаёт сам FastAPI.
**Почему.** Нет этапа сборки и Node.js — на Windows-ноутбуке и сервере ставится только
Docker; меньше слоёв, которые нужно объяснять; интерфейс — карта и формы, реактивный
фреймворк здесь не обязателен.
**Отброшено.** Vue 3 + Vite (лишняя инфраструктура сборки), React.

## ADR-04. Граф сети в памяти (NetworkX), строится из базы
**Решение.** Для трассировки и локализации граф собирается из таблиц `splice`,
`cable_route`, `fiber`, `cross_port`; алгоритмы — на NetworkX.
**Почему.** Сеть — тысячи узлов, граф строится за доли секунды; алгоритмы на Python
легко тестировать и описывать в ВКР.
**Отброшено.** pgRouting (сложнее отлаживать бизнес-правила: концы волокон, запасы,
укрутка), графовая СУБД (лишний компонент).

## ADR-05. Нормализованная рассветка
**Решение.** Сварка — строка таблицы между двумя концами волокон.
**Почему.** Только так возможны трассировка, анализ последствий и проверка «одно
волокно — одна сварка» средствами базы.
**Отброшено.** JSON-паспорт муфты — по нему нельзя построить граф и проверить
целостность.

## ADR-06. Достоверность длин
**Решение.** У каждой длины — источник с погрешностью; локализация выдаёт интервал.
**Почему.** Длины в сети разного качества (рефлектометр, ИД, «со слов», по карте);
без учёта этого результат локализации выглядит точнее, чем есть.

## ADR-07. Импорт в два шага (разбор → подтверждение)
**Решение.** Любой импорт сначала строит предпросмотр и отчёт, запись — после
подтверждения, в одной транзакции.
**Почему.** Входные данные «грязные» (KML без атрибутов, ИД с ошибками); пользователь
должен видеть и поправить результат до попадания в базу.

## ADR-08. Правила разбора ИД — в конфигурации
**Решение.** Правила классификации страниц и шаблоны извлечения — в YAML, ядро парсера
от них не зависит.
**Почему.** Формы ИД у подрядчиков могут различаться; новую форму можно добавить без
изменения кода.

## ADR-09. Планировщик внутри приложения (APScheduler)
**Решение.** Опрос узлов — задача APScheduler в процессе приложения.
**Почему.** Одна периодическая задача раз в 5 минут; Celery + Redis добавили бы два
сервиса без пользы. Режим `simulate` на ноутбуке (нет доступа к сети узлов),
`ping` — на сервере.

## ADR-10. Пароли — scrypt из стандартной библиотеки, токены — JWT
**Решение.** `hashlib.scrypt` для паролей, JWT в cookie `HttpOnly` для сессии.
**Почему.** Нет нативных зависимостей (bcrypt/argon2 требуют компиляции на части
платформ); scrypt — стойкая функция хэширования паролей. `HttpOnly` защищает токен от
чтения скриптами страницы.

## ADR-11. Тяжёлые зависимости — необязательные
**Решение.** EasyOCR (PyTorch, ~2 ГБ), pyogrio (Shapefile), pyproj вынесены в
дополнительные группы зависимостей.
**Почему.** Основной образ остаётся лёгким; Tesseract покрывает OCR ИД, PostGIS —
пересчёт координат. EasyOCR нужен только для сравнительного эксперимента.

## ADR-12. Тесты на настоящем PostGIS
**Решение.** Тесты работают с PostgreSQL + PostGIS (локально и в CI), не с SQLite.
**Почему.** Ключевая логика опирается на пространственные функции, которые в SQLite
не проверить.

## ADR-13. Слои карты — GeoJSON, собранный в PostGIS
**Решение.** Каждый слой отдаётся одним SQL-запросом, который сам строит FeatureCollection.
**Почему.** Нет преобразования «строка БД → объект Python → JSON»; ответ 8–26 мс. Фильтры
(оператор, владелец, видимая область) — условия того же запроса.
**Отброшено.** Сериализация через ORM и Pydantic (в разы медленнее на тысячах объектов),
векторные тайлы (избыточны для объёма сети одной компании).

## ADR-14. Собственная сеточная кластеризация вместо Leaflet.markercluster
**Решение.** Точки группируются по ячейкам экранной сетки (js/cluster.js, ~50 строк).
**Почему.** Плагин распространяется только через npm-сборку; своя реализация прозрачна,
O(n), легко объясняется. Библиотеки фронтенда лежат в проекте (frontend/vendor), а не
грузятся с CDN — система работает и в закрытой сети предприятия.

## ADR-15. Сессия в cookie HttpOnly, а не токен в localStorage
**Решение.** JWT в cookie HttpOnly + SameSite=Lax + обязательный X-Requested-With для
изменяющих запросов.
**Почему.** Токен в localStorage доступен любому внедрённому скрипту; cookie HttpOnly — нет.
Защита от CSRF обеспечивается SameSite и заголовком, который чужой сайт не может отправить.

## ADR-16. Привязка концов линий: код → расстояние → новая точка
**Решение.** Сначала код из названия (до 300 м), затем ближайший узел в допуске (10 м),
иначе новая точка; ориентация линии выбирается по совпадению кодов.
**Почему.** Атрибутов в KML нет, а названия несут топологию; одной только близости
недостаточно (концы бывают в десятках метров от колодца), одного кода — тоже (опечатки,
неуникальные коды). Комбинация даёт привязку и одновременно выявляет ошибки в данных.

## ADR-17. При подтверждении импорта план строится заново
**Решение.** Хранится исходный файл и сопоставление папок; запись — по свежему плану.
**Почему.** Между предпросмотром и подтверждением база могла измениться (другой импорт,
правки); хранить «устаревший» план и применять его вслепую — риск дублей.

## ADR-18. Кабель — цепочка участков, путь — Дейкстра по лучшей известной длине
**Решение.** Кабель хранит маршрут как упорядоченный список участков с направлением; при
прокладке путь между опорными точками ищется по графу трасс с весом «фактическая длина,
иначе по карте».
**Почему.** Так геометрия и длина кабеля всегда согласованы с трассами, а правка трассы
автоматически меняет все кабели на ней. Опорные точки покрывают случаи, когда кабель идёт
не кратчайшим путём, без ручного рисования линии кабеля.
**Отброшено.** Рисование кабеля отдельной линией (расходится с трассами, длину нельзя
вычислить по участкам), pgRouting (граф и так строится за миллисекунды, см. ADR-04).

## ADR-19. Привязка при рисовании: пиксели в интерфейсе + метры на сервере
**Решение.** Интерфейс прилипает к точке ближе 15 пикселей; сервер, получив координаты,
ищет точку в радиусе 3 м и использует её.
**Почему.** Экранный допуск одинаково удобен на любом масштабе, а серверный гарантирует
отсутствие дублей, даже если запрос пришёл не из интерфейса или точки ещё не загружены.

## ADR-20. Очистка тестовой сети по происхождению данных
**Решение.** Удаляются только объекты с `source_kind = 'generator'`; узел, к которому
привязались импортированные объекты, остаётся и попадает в отчёт.
**Почему.** Генератор и реальный импорт живут в одной базе; полный сброс уничтожил бы
работу пользователя, а поле происхождения уже есть у всех объектов (этап 2).

## ADR-21. Транзит — это сварки, а не «кабель без разреза в муфте»
**Решение.** Чтобы работать с волокнами кабеля в муфте, кабель разрезается на две части,
а нетронутые волокна соединяются транзитными сварками.
**Почему.** Модель остаётся единообразной: любое соединение волокон — строка `splice`,
трассировка (этап 7) идёт только по сваркам и портам, без особых случаев. Ответвление
делается заменой одной транзитной сварки.
**Отброшено.** Хранить «вскрытые» волокна прямо в маршруте кабеля — усложняет и
проверку целостности, и обход графа.

## ADR-22. Групповые операции в точке сохранения
**Решение.** Групповая сварка и подключение портов выполняются в SAVEPOINT; объекты
добавляются внутри него.
**Почему.** Триггер базы может отклонить любое соединение из группы; без точки
сохранения ошибка ломает всю транзакцию запроса, а частичная запись путает монтажника.

## ADR-23. Документы: белый список и проверка подписи для показа в браузере
**Решение.** Загрузка — только разрешённых расширений; inline-показ — только для PDF и
изображений с верной сигнатурой, остальное — скачивание с `nosniff`.
**Почему.** Система открыта в одном источнике (origin) с API; файл, показанный браузером
как HTML, мог бы выполнить скрипт от имени пользователя.

## ADR-24. Интервал погрешности — сумма дисперсий по источникам длины
**Решение.** h = 2·√Σσ²: ошибки длин элементов независимы, укрутка — одна ошибка на
кабель, плюс погрешность прибора. Каждое слагаемое показывается пользователю.
**Почему.** Простая и проверяемая модель, которую можно объяснить и откалибровать;
разложение по вкладам превращает интервал в подсказку, какие длины уточнить.
**Отброшено.** Метод Монте-Карло в реальном времени (тот же результат при нормальных
ошибках, но дольше и сложнее объяснить), фиксированный допуск «±50 м» (не отражает
качество данных).

## ADR-25. Точка внутри участка — по доле длины, а не по метрам карты
**Решение.** Положение внутри участка переносится на нарисованную линию пропорционально
(доля фактической длины = доля длины линии).
**Почему.** Карта нарисована схематично; откладывать «паспортные» метры по линии карты
значило бы выходить за конец участка или не доходить до него.

## ADR-26. Проверка локализации на синтетической сети с известной истиной
**Решение.** Генератор хранит истинные длины и укрутку (sim_truth), эксперимент
моделирует повреждения и сравнивает прогноз с истиной.
**Почему.** Реальных повреждений с точно известным местом мало, а на синтетике можно
измерить и ошибку, и честность интервала (долю попаданий) на сотнях случаев.

## ADR-27. Калибровка — МНК с априорными значениями, а не «среднее отклонение»
**Решение.** Параметры (укрутка по маркам, поправка карты) оцениваются взвешенным МНК
с регуляризацией к типовым значениям, методом Гаусса–Ньютона; погрешности — из
ковариационной матрицы.
**Почему.** Наблюдения — суммы по разным кабелям и участкам; простое усреднение не
разделяет вклады. Регуляризация не даёт подогнать параметры под шум при малых данных,
а ковариация отвечает на вопрос «можно ли этому верить» и сужает интервал локализации.
**Отброшено.** Подбор укрутки на каждый кабель (данных на кабель мало — переобучение),
нейросети и градиентный бустинг (непрозрачно, мало данных).

## ADR-28. Калибровка не меняет данные до подтверждения
**Решение.** Расчёт сохраняет прогон с предложениями и метриками; применение — отдельное
действие администратора с возможностью отката (прежние значения хранятся в прогоне).
Проверка на моделировании выполняется во временной точке сохранения с откатом.
**Почему.** Калибровка меняет все последующие прогнозы — это решение человека, а не побочный
эффект нажатия «рассчитать»; откат нужен, если данные для калибровки оказались ошибочными.

## ADR-29. Разбор ИД в фоновом потоке, а не в очереди задач
**Решение.** Загрузка сохраняет файл и запись пакета со статусом «processing», разбор
выполняется в отдельном потоке приложения с собственной сессией базы; ход разбора
пишется в запись пакета, интерфейс опрашивает её.
**Почему.** Пакеты загружаются единицами в день; очередь (Celery + Redis) добавила бы два
сервиса ради редких задач. Прерванный перезапуском разбор распознаётся по времени и
помечается ошибкой — пользователь загрузит файл заново.

## ADR-30. Синтетический пакет ИД для тестов
**Решение.** Тесты разбора работают на PDF, который генерируется кодом (reportlab) с
вымышленными данными и заложенными ошибками.
**Почему.** Реальные ИД содержат персональные данные и не могут лежать в репозитории;
синтетический пакет к тому же даёт заранее известный набор ошибок, который проверка
обязана найти.

## ADR-31. Мобильная версия — тот же веб-интерфейс, а не нативное приложение
**Решение.** Телефон монтажника открывает ту же систему в браузере; интерфейс свёрстан
адаптивно (нижняя шторка, крупные кнопки), функции выезда (рядом, маршрут, GPS, камера)
используют стандартные API браузера.
**Почему.** Одна кодовая база, обновление сразу у всех без магазинов приложений и
установки, работа на Android и iPhone. Нативные возможности, которые нужны на выезде,
браузер даёт.
**Отброшено.** Отдельное приложение на Kotlin/Swift или Flutter — вдвое больше кода и
сопровождения ради функций, доступных в браузере.

## ADR-32. HTTPS в локальной сети через Caddy с локальным центром сертификации
**Решение.** Перед приложением — контейнер Caddy с `tls internal`: сертификат на IP-адрес
ноутбука/сервера (`PHONE_HOST`) выпускает собственный центр сертификации Caddy; корневой
сертификат можно установить на телефон со страницы «Вход с телефона».
**Почему.** Геолокация и камера в браузере доступны только по https. Let's Encrypt не
выдаёт сертификаты на частные IP и требует доступа из интернета; самоподписанный
сертификат, сделанный вручную, пришлось бы перевыпускать и раздавать — Caddy делает это сам.
**Отброшено.** nginx + openssl (ручной выпуск и продление), туннели во внешний интернет
(ngrok и т. п.) — данные сети не должны уходить за пределы компании.

## ADR-33. Маршрут до места — ссылкой в Яндекс Карты
**Решение.** Кнопка «Маршрут» открывает Яндекс Карты/Навигатор с точкой назначения.
**Почему.** Построение маршрута по дорогам требует графа улиц и пробок — это задача
картографического сервиса, а не учётной системы; у монтажников навигатор уже установлен.

## ADR-34. Корреляция аварий по схеме, а не по топологии IP-сети
**Решение.** Вероятное место обрыва ищется среди участков трассы, общих для линейных
трактов всех недоступных узлов и не входящих в тракты доступных. Тракты берутся
трассировкой волокна по сварочным схемам.
**Почему.** Система знает физический путь света, а не только логические связи
коммутаторов. Именно физический путь отвечает на вопрос «куда ехать», и сразу даёт окно
на рефлектометре. Логическая зависимость (uplink) проверяется отдельно, чтобы отличить
обрыв кабеля от аварии коммутатора.
**Отброшено.** Вероятностные модели (байесовские сети, обучение на истории аварий):
истории аварий нет, а результат нужно объяснять дежурному.

## ADR-35. Опрос узлов — поток приложения с блокировкой в базе
**Решение.** Опрос идёт в фоновом потоке приложения. От двойного опроса при нескольких
процессах защищает `pg_try_advisory_xact_lock`. Все адреса опрашиваются одним вызовом
`fping`.
**Почему.** Опрос раз в несколько минут нескольких сотен адресов — лёгкая задача.
Отдельный сервис или очередь задач добавили бы компоненты без выигрыша. Блокировка в
PostgreSQL не требует дополнительной инфраструктуры.
**Отброшено.** Zabbix и аналоги как источник статусов. Это возможное развитие: модуль
опроса заменяется интеграцией по API, а анализ последствий и корреляция остаются.

## ADR-36. Режим имитации мониторинга по физике сети
**Решение.** На ноутбуке ответы узлов вычисляются из имитированных аварий (обрыв
участка, нет питания) по тем же трактам, что использует анализ последствий. Корреляция
получает только статусы.
**Почему.** Так демонстрация и проверка алгоритма корреляции честные: правильный ответ
известен имитатору, но не алгоритму, и можно считать точность (этап 12).

## ADR-37. Координаты фото: EXIF, затем OCR подписи
**Решение.** Координаты съёмки берутся из EXIF. Если их нет, подпись «GPS-камеры»
распознаётся Tesseract, который уже используется для пакетов ИД. Найденная точка
сопоставляется с ближайшей точкой сети (до 25 м — то же место).
**Почему.** Фото с объектов часто приходят через мессенджеры без EXIF, а приложения
с впечатанными координатами распространены у монтажников. HEIC не поддерживается:
браузер iPhone при загрузке через страницу сам переводит снимок в JPEG.
