# Архитектурные решения

Каждое решение: что выбрано, почему, какие варианты отброшены.

## ADR-01. Модульный монолит вместо микросервисов
**Решение.** Одно приложение FastAPI (API + статика + планировщик) и одна база.
**Почему.** Пользователей единицы–десятки, нагрузка мала; монолит проще развернуть на
ноутбуке и перенести на сервер компании, а модули сервисного слоя всё равно разделены.
**Отброшено.** Микросервисы (импорт, граф, мониторинг отдельно) — лишняя сложность
развёртывания и межсервисного взаимодействия без выигрыша при такой нагрузке.

## ADR-02. PostgreSQL + PostGIS
**Решение.** Хранение геометрии и пространственные запросы в PostGIS.
**Почему.** Привязка концов линий (`ST_DWithin`), длины по эллипсоиду (`geography`),
точка на линии по расстоянию (`ST_LineInterpolatePoint`), пересчёт систем координат
(`ST_Transform`) — всё есть в базе и выполняется с пространственными индексами.
**Отброшено.** SQLite/SpatiaLite (слабее для многопользовательской работы), хранение
координат числами без пространственного индекса.

## ADR-03. Фронтенд на JavaScript без сборщика вместо Vue
**Решение.** HTML + ES-модули + Leaflet, файлы отдаёт сам FastAPI.
**Почему.** Нет этапа сборки и Node.js — на Windows-ноутбуке и сервере ставится только
Docker; меньше слоёв, которые нужно объяснять; интерфейс — карта и формы, реактивный
фреймворк здесь не обязателен.
**Отброшено.** Vue 3 + Vite (лишняя инфраструктура сборки), React.

## ADR-04. Граф сети в памяти (NetworkX), строится из базы
**Решение.** Для трассировки и локализации граф собирается из таблиц `splice`,
`cable_route`, `fiber`, `cross_port`; алгоритмы — на NetworkX.
**Почему.** Сеть — тысячи узлов, граф строится за доли секунды; алгоритмы на Python
легко тестировать и описывать в ВКР.
**Отброшено.** pgRouting (сложнее отлаживать бизнес-правила: концы волокон, запасы,
укрутка), графовая СУБД (лишний компонент).

## ADR-05. Нормализованная рассветка
**Решение.** Сварка — строка таблицы между двумя концами волокон.
**Почему.** Только так возможны трассировка, анализ последствий и проверка «одно
волокно — одна сварка» средствами базы.
**Отброшено.** JSON-паспорт муфты — по нему нельзя построить граф и проверить
целостность.

## ADR-06. Достоверность длин
**Решение.** У каждой длины — источник с погрешностью; локализация выдаёт интервал.
**Почему.** Длины в сети разного качества (рефлектометр, ИД, «со слов», по карте);
без учёта этого результат локализации выглядит точнее, чем есть.

## ADR-07. Импорт в два шага (разбор → подтверждение)
**Решение.** Любой импорт сначала строит предпросмотр и отчёт, запись — после
подтверждения, в одной транзакции.
**Почему.** Входные данные «грязные» (KML без атрибутов, ИД с ошибками); пользователь
должен видеть и поправить результат до попадания в базу.

## ADR-08. Правила разбора ИД — в конфигурации
**Решение.** Правила классификации страниц и шаблоны извлечения — в YAML, ядро парсера
от них не зависит.
**Почему.** Формы ИД у подрядчиков могут различаться; новую форму можно добавить без
изменения кода.

## ADR-09. Планировщик внутри приложения (APScheduler)
**Решение.** Опрос узлов — задача APScheduler в процессе приложения.
**Почему.** Одна периодическая задача раз в 5 минут; Celery + Redis добавили бы два
сервиса без пользы. Режим `simulate` на ноутбуке (нет доступа к сети узлов),
`ping` — на сервере.

## ADR-10. Пароли — scrypt из стандартной библиотеки, токены — JWT
**Решение.** `hashlib.scrypt` для паролей, JWT в cookie `HttpOnly` для сессии.
**Почему.** Нет нативных зависимостей (bcrypt/argon2 требуют компиляции на части
платформ); scrypt — стойкая функция хэширования паролей. `HttpOnly` защищает токен от
чтения скриптами страницы.

## ADR-11. Тяжёлые зависимости — необязательные
**Решение.** EasyOCR (PyTorch, ~2 ГБ), pyogrio (Shapefile), pyproj вынесены в
дополнительные группы зависимостей.
**Почему.** Основной образ остаётся лёгким; Tesseract покрывает OCR ИД, PostGIS —
пересчёт координат. EasyOCR нужен только для сравнительного эксперимента.

## ADR-12. Тесты на настоящем PostGIS
**Решение.** Тесты работают с PostgreSQL + PostGIS (локально и в CI), не с SQLite.
**Почему.** Ключевая логика опирается на пространственные функции, которые в SQLite
не проверить.

## ADR-13. Слои карты — GeoJSON, собранный в PostGIS
**Решение.** Каждый слой отдаётся одним SQL-запросом, который сам строит FeatureCollection.
**Почему.** Нет преобразования «строка БД → объект Python → JSON»; ответ 8–26 мс. Фильтры
(оператор, владелец, видимая область) — условия того же запроса.
**Отброшено.** Сериализация через ORM и Pydantic (в разы медленнее на тысячах объектов),
векторные тайлы (избыточны для объёма сети одной компании).

## ADR-14. Собственная сеточная кластеризация вместо Leaflet.markercluster
**Решение.** Точки группируются по ячейкам экранной сетки (js/cluster.js, ~50 строк).
**Почему.** Плагин распространяется только через npm-сборку; своя реализация прозрачна,
O(n), легко объясняется. Библиотеки фронтенда лежат в проекте (frontend/vendor), а не
грузятся с CDN — система работает и в закрытой сети предприятия.

## ADR-15. Сессия в cookie HttpOnly, а не токен в localStorage
**Решение.** JWT в cookie HttpOnly + SameSite=Lax + обязательный X-Requested-With для
изменяющих запросов.
**Почему.** Токен в localStorage доступен любому внедрённому скрипту; cookie HttpOnly — нет.
Защита от CSRF обеспечивается SameSite и заголовком, который чужой сайт не может отправить.

## ADR-16. Привязка концов линий: код → расстояние → новая точка
**Решение.** Сначала код из названия (до 300 м), затем ближайший узел в допуске (10 м),
иначе новая точка; ориентация линии выбирается по совпадению кодов.
**Почему.** Атрибутов в KML нет, а названия несут топологию; одной только близости
недостаточно (концы бывают в десятках метров от колодца), одного кода — тоже (опечатки,
неуникальные коды). Комбинация даёт привязку и одновременно выявляет ошибки в данных.

## ADR-17. При подтверждении импорта план строится заново
**Решение.** Хранится исходный файл и сопоставление папок; запись — по свежему плану.
**Почему.** Между предпросмотром и подтверждением база могла измениться (другой импорт,
правки); хранить «устаревший» план и применять его вслепую — риск дублей.

## ADR-18. Кабель — цепочка участков, путь — Дейкстра по лучшей известной длине
**Решение.** Кабель хранит маршрут как упорядоченный список участков с направлением; при
прокладке путь между опорными точками ищется по графу трасс с весом «фактическая длина,
иначе по карте».
**Почему.** Так геометрия и длина кабеля всегда согласованы с трассами, а правка трассы
автоматически меняет все кабели на ней. Опорные точки покрывают случаи, когда кабель идёт
не кратчайшим путём, без ручного рисования линии кабеля.
**Отброшено.** Рисование кабеля отдельной линией (расходится с трассами, длину нельзя
вычислить по участкам), pgRouting (граф и так строится за миллисекунды, см. ADR-04).

## ADR-19. Привязка при рисовании: пиксели в интерфейсе + метры на сервере
**Решение.** Интерфейс прилипает к точке ближе 15 пикселей; сервер, получив координаты,
ищет точку в радиусе 3 м и использует её.
**Почему.** Экранный допуск одинаково удобен на любом масштабе, а серверный гарантирует
отсутствие дублей, даже если запрос пришёл не из интерфейса или точки ещё не загружены.

## ADR-20. Очистка тестовой сети по происхождению данных
**Решение.** Удаляются только объекты с `source_kind = 'generator'`; узел, к которому
привязались импортированные объекты, остаётся и попадает в отчёт.
**Почему.** Генератор и реальный импорт живут в одной базе; полный сброс уничтожил бы
работу пользователя, а поле происхождения уже есть у всех объектов (этап 2).
